## Context

当前 Violet 的关系推进流程中，ICEBREAKING → FLIRTING 过渡已在 `ChatLifecycleService.onFlirting()` 中实现了军师退出和聊天室只读化。但需求文档明确要求"双方互相同意进入暧昧期后，系统自动交换注册时的微信/QQ"，这一功能尚未实现。

用户模型中 `wechat` 和 `qq` 字段已存在于 Prisma schema，但：
- 后端 `updateProfile` 的 body 类型未包含这两个字段，用户无法编辑
- 前端个人中心没有对应的输入 UI
- `phone` 字段在 schema 中不存在

现有的隐私隔离已经到位：`getPublicProfile()` 只 select id/nickname/avatar，`getAnonymousProfile()` 不包含联系方式，`DiscoveryService.listUsers()` 也不暴露这些字段。

## Goals / Non-Goals

**Goals:**
- 用户可在个人中心编辑微信号、QQ号（"交换信息"折叠栏）和手机号（"账号安全"折叠栏）
- 暧昧期过渡时自动查询并推送双方微信号和QQ号给当事人
- 前端暧昧期弹窗展示对方联系方式并支持一键复制
- 保证联系方式仅对当事人双方可见，军师和其他用户不可见

**Non-Goals:**
- 不实现军师评价与信用分结算（这是独立功能，后续单独实现）
- 不实现手机号交换（需求文档只要求交换微信/QQ）
- 不实现联系方式的端到端加密（当前阶段平台可信）

## Decisions

### 1. 联系方式存储：直接使用 User 表字段

**选择**: 在现有 User 模型的 `wechat`、`qq` 字段上添加前端编辑能力，新增 `phone` 字段。

**替代方案**: 创建独立的 ContactInfo 表。
**理由**: 联系方式与用户 1:1 关系，不需要独立表。现有字段已存在，无需过度设计。

### 2. 交换时机：onFlirting() 内完成

**选择**: 在 `ChatLifecycleService.onFlirting()` 中查询双方 wechat/qq，生成系统消息，并通过 socket 事件 `contactExchange` 推送给双方。

**替代方案**: 前端进入暧昧期后主动调用 REST API 获取对方联系方式。
**理由**: 交换是关系状态变更的原子操作，应与状态转换在同一事务中完成。用系统消息可以留存记录，用 socket 事件可以驱动前端实时 UI。REST API 方案需要额外接口且无法保证原子性。

### 3. 系统消息 + socket 事件双通道

**选择**:
- 系统消息（type=SYSTEM）：在聊天记录中留存"联系方式已交换"记录，内容包含双方联系方式
- socket 事件 `contactExchange`：携带结构化数据（对方 wechat/qq），前端用于展示复制按钮

**理由**: 系统消息作为历史记录持久化，socket 事件用于实时 UI 交互。回看聊天记录时也能看到交换了什么。

### 4. 前端展示：扩展现有暧昧期弹窗

**选择**: 在现有的 `isFlirting` 弹窗中增加联系方式展示区域，包含对方微信号和QQ号及复制按钮。

**替代方案**: 新增独立的联系方式展示页面。
**理由**: 现有弹窗已有"恭喜进入暧昧期"的 UI，联系方式是同一流程的延续，放在一起体验更连贯。

## Risks / Trade-offs

- **[用户未填写联系方式]** → 前端"交换信息"栏提示"请至少填写一项"。onFlirting 时如果对方未填写，展示"对方未设置"而非留空。
- **[系统消息中明文存储联系方式]** → 这是可接受的，聊天记录本身只有当事人双方和已退出的军师可以查看。未来如需加密可以升级。
- **[socket 事件可能丢失]** → 用户重新进入聊天室时，历史系统消息中已包含联系方式，可以回看。无需额外持久化。
