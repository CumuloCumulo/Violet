# 架构候选方案对比

## 一、候选方案概述

### 方案 A：前后端分离的单体分层架构

采用经典的 B/S 前后端分离架构，后端使用 NestJS 框架构建单体应用，内部按业务领域划分为多个模块（Auth、User、Chat、Discovery 等），每个模块内部遵循 Controller → Service → Repository 三层结构。前端使用 React SPA，通过 RESTful API 和 WebSocket 与后端通信。

```
┌─────────────────────────────────────────────────┐
│                   Nginx 反向代理                   │
├──────────────────────┬──────────────────────────┤
│   静态资源 (React SPA)  │   API 代理 (/api → :3000)   │
└──────────────────────┴──────────────────────────┘
                            │
                   ┌────────┴────────┐
                   │   NestJS 单体应用  │
                   │  ┌─────────────┐ │
                   │  │  Controller  │ │
                   │  ├─────────────┤ │
                   │  │   Service    │ │
                   │  ├─────────────┤ │
                   │  │ Prisma (ORM) │ │
                   │  └──────┬──────┘ │
                   └─────────┼────────┘
                    ┌────────┴────────┐
                    │   PostgreSQL     │
                    │   Redis          │
                    └─────────────────┘
```

### 方案 B：微服务架构

将系统按业务领域拆分为独立部署的微服务，包括用户服务、匹配服务、聊天服务、军师任务服务、信用服务、管理服务等。服务之间通过消息队列（如 RabbitMQ）进行异步通信，通过 API Gateway 统一入口。每个微服务拥有独立的数据库实例（Database per Service 模式）。

```
┌──────────────────────────────────────────────┐
│                   API Gateway                    │
├──────┬───────┬──────────┬──────────┬─────────┤
│用户服务│匹配服务│ 聊天服务   │军师任务服务│ 管理服务  │
│  DB  │  DB   │   DB     │   DB     │   DB    │
└──────┴───────┴──────────┴──────────┴─────────┘
            │          │
        ┌───┴───┐  ┌──┴───┐
        │RabbitMQ│  │Redis │
        └───────┘  └──────┘
```

## 二、多维度对比

| 对比维度 | 方案 A：单体分层架构 | 方案 B：微服务架构 |
|---------|-------------------|-----------------|
| **开发复杂度** | **低。** 单一代码仓库，统一的构建和部署流程，模块间通过方法调用直接通信，无需处理网络序列化和分布式事务。 | **高。** 需要为每个微服务单独搭建项目结构、定义 API 契约、处理服务发现、负载均衡、分布式事务（Saga 模式）等分布式系统问题。 |
| **可维护性** | **中等。** 模块边界通过 NestJS Module 系统强制隔离，代码组织清晰。但随着功能增长，模块间可能出现隐式耦合。项目当前规模下（~8 个模块）可维护性良好。 | **高。** 每个服务独立代码库，边界明确。但跨服务的功能变更需要协调多个仓库，调试链路追踪复杂。 |
| **可扩展性** | **有限。** 只能整体水平扩展（多实例 + 负载均衡），无法针对聊天等高负载模块单独扩容。对于校园级应用，这通常不是瓶颈。 | **高。** 可按服务粒度独立扩缩容，聊天服务可单独增加实例。但对本项目而言属于过度设计。 |
| **性能** | **优。** 模块间本地方法调用，无网络开销；单数据库事务，数据一致性强；WebSocket 连接管理简单集中。 | **中等。** 服务间网络通信增加延迟；分布式事务降低吞吐；消息队列引入额外延迟。对于校园级并发量，性能优势无法体现，反而增加开销。 |
| **团队学习成本** | **低。** NestJS + React 是主流技术栈，团队成员上手快；Prisma ORM 学习曲线平缓；部署仅需一台服务器。 | **高。** 需要掌握 Docker/Kubernetes 容器编排、服务网格、分布式追踪、消息队列等额外技术栈，学习成本显著增加。 |
| **10 周内可行性** | **高。** 单代码库集中开发，CI/CD 流程简单，部署快捷。团队可以快速迭代核心功能，不需要在基础设施上投入过多时间。 | **低。** 基础设施搭建（服务发现、配置中心、日志聚合等）本身就需要数周时间，挤压业务开发时间。4 人团队在 10 周内难以同时维护 6+ 个服务的开发、测试和部署。 |

## 三、最终选择

### 选定方案：方案 A — 前后端分离的单体分层架构

### 选择理由

1. **项目规模匹配**：Violet 是面向校园场景的恋爱辅助平台（核心特色为「军师代聊」模式），预计用户量在千级，单体架构完全能满足性能和可扩展性需求。

2. **时间约束**：10 周开发周期紧张，团队 4 人，单体架构允许快速迭代，避免在分布式基础设施上消耗过多精力。

3. **技术风险可控**：单体应用的故障模式简单，不存在分布式系统的网络分区、服务雪崩等复杂问题。

4. **团队效率**：统一的代码仓库便于代码审查和协作，NestJS 模块系统已提供良好的模块边界。

5. **渐进式演进**：如果未来需要，NestJS 的模块化设计使得将单个模块拆分为微服务（如聊天服务）是可行的，架构具备演进能力。

### 不选方案 B 的原因

微服务架构虽然在大规模系统中优势明显，但对 Violet 项目而言属于过度设计：团队规模不足以同时维护多个服务、10 周内难以完成基础设施搭建、校园级并发量无法体现微服务的扩展优势。引入的复杂度远超收益。
