# ADR-001：采用前后端分离的单体分层架构
## 状态
已接受

## 背景
Violet 是面向南京大学的校园恋爱辅助平台，核心功能包括用户发现（灵魂画廊）、牵线匹配、三边/四边实时聊天室（含军师代聊）、军师任务大厅、信用积分系统和管理后台。团队 4 人，开发周期 10 周。需要在有限时间内完成 MVP 并部署上线。

## 决策
我们决定采用前后端分离的单体分层架构：

+ 前端：React SPA（Vite 构建）
+ 后端：NestJS 单体应用，内部按业务领域划分为独立模块
+ 数据层：PostgreSQL + Redis
+ 部署：单台阿里云 ECS，Nginx 反向代理

## 理由
**AI 初稿建议：**  
AI 建议采用微服务架构以获得更好的可扩展性和独立部署能力，同时推荐使用 Next.js 的 SSR 能力提升首屏加载速度。

**人工修订：**

1. 拒绝微服务方案：校园级应用预计千级用户，微服务属于过度设计，且 4 人团队在 10 周内难以搭建分布式基础设施
2. 拒绝 Next.js SSR：Violet 是重交互的 SPA 应用（实时聊天、动画交互），SSR 的 SEO 优势和首屏加载优化对本项目价值有限，反而增加开发复杂度
3. 选择单体架构：NestJS 的模块系统已提供良好的业务边界划分，未来如有需要可将单个模块（如 Chat）拆分为独立服务

## 后果
+ 正面影响：开发效率高，部署简单，团队可快速迭代
+ 负面影响：无法针对单个模块独立扩缩容
+ 需要关注的风险：随着功能增长，需严格维护模块边界，防止单体退化为"大泥球"

## AI 辅助记录
+ AI 初稿内容摘要：建议微服务 + Next.js SSR，强调可扩展性和 SEO 优势
+ 人工修订内容：改为单体分层 + React SPA，明确校园场景下微服务不适用
+ 修订理由：AI 忽略了团队规模（4人）和时间约束（10周），给出的建议适用于中大型商业项目而非校园实训项目

# ADR-002：使用 Socket.io 实现三边/四边聊天室
## 状态
已接受

## 背景
Violet 的核心特色是军师代聊机制，需要一个聊天室系统支持：

1. 当事人双方的主聊天窗口
2. 军师与己方当事人的私聊窗口
3. 军师三种介入模式（私聊/辅助/Solo）下的不同消息可见性规则
4. 关系状态流转（牵线→破冰→暧昧→结束）时的聊天室生命周期管理
5. 在线状态追踪

## 决策
采用 Socket.io 实现实时聊天，配合 Redis 管理在线状态和房间成员信息。

## 理由
**AI 初稿建议：**  
AI 建议使用原生 WebSocket（ws 库）+ 自定义事件协议，认为 Socket.io 的轮询降级机制和额外开销是不必要的。

**人工修订：**

1. 选择 Socket.io 而非原生 WebSocket：Socket.io 提供了开箱即用的房间管理、命名空间、自动重连、事件广播等能力，与 NestJS 的 WebSocket 集成成熟
2. 聊天室架构设计为「关系 ID → 房间」的映射，每个 Relationship 对应一个 Socket.io Room，房间成员包括双方当事人和各自的军师
3. 消息可见性由后端 `computeVisibility()` 方法根据发送者角色和军师模式动态计算，而非依赖前端的过滤逻辑
4. 使用 Redis 存储在线状态而非数据库，减少查询延迟

## 后果
+ 正面影响：开发效率高，房间和广播机制直接映射业务模型，自动重连提升用户体验
+ 负面影响：Socket.io 协议非标准 WebSocket，客户端必须使用 Socket.io 客户端库
+ 需要关注的风险：多角色聊天室的可见性逻辑复杂，需要充分的测试覆盖

## AI 辅助记录
+ AI 初稿内容摘要：推荐原生 WebSocket + 自定义协议，认为 Socket.io 过重
+ 人工修订内容：坚持使用 Socket.io，利用其房间管理和自动重连等内置能力
+ 修订理由：AI 低估了三边/四边聊天室的复杂度，原生 WebSocket 需要从零实现房间管理、重连、广播等功能，开发成本远高于引入 Socket.io 库的代价

# ADR-003：使用 Prisma ORM 而非原生 SQL 或 TypeORM
## 状态
已接受

## 背景
Violet 的数据模型包含用户、关系、军师任务、消息、匹配请求、评分、帖子等实体，关系复杂（多对多、自引用、枚举状态等）。需要选择数据库访问层技术。

## 决策
采用 Prisma 作为 ORM，配合 PostgreSQL 数据库。

## 理由
**AI 初稿建议：**  
AI 建议使用 TypeORM，理由是与 NestJS 的官方集成更成熟，社区示例更多，且支持 Active Record 和 Data Mapper 两种模式。

**人工修订：**

1. 选择 Prisma 而非 TypeORM：
    - Prisma 的 Schema 定义语法更直观（声明式 `.prisma` 文件），TypeORM 使用装饰器语法，模型定义与验证逻辑混杂
    - Prisma 的类型推断更精确，查询结果自动推导类型，无需手动定义返回类型
    - Prisma 的迁移管理更可靠（`prisma migrate`），TypeORM 的自动同步在生产环境存在风险
    - Prisma 的查询 API 更符合直觉（`prisma.user.findMany()` vs `repository.find()`）
2. 选择 PostgreSQL 而非 MySQL：PostgreSQL 对 JSON 字段、枚举类型、复杂查询的支持更好，适合 Violet 中灵活的用户标签和兴趣数据存储

## 后果
+ 正面影响：类型安全的数据库访问，Schema 即文档，迁移管理可靠，开发体验好
+ 负面影响：Prisma 不支持多对多关系的自定义中间表字段（需使用显式模型替代），部分复杂查询需要回退到 `$queryRaw`
+ 需要关注的风险：Prisma 的抽象层在某些复杂查询场景（如动态过滤、聚合）下可能成为限制

## AI 辅助记录
+ AI 初稿内容摘要：推荐 TypeORM，强调与 NestJS 的官方集成和社区生态
+ 人工修订内容：改为 Prisma，重点考量类型安全和开发体验
+ 修订理由：AI 过度依赖"官方推荐"和"社区规模"做判断，忽略了 Prisma 在类型安全、Schema 定义、迁移管理方面的实际开发体验优势。实际使用中 Prisma 的 TypeScript 集成远优于 TypeORM

# ADR-004：基于 Cookie 的 JWT 认证方案
## 状态
已接受

## 背景
Violet 需要用户认证系统，保护 API 端点和 WebSocket 连接。系统同时包含普通用户（当事人/军师）和管理员角色。注册需限制南京大学 smail 邮箱。

## 决策
采用 JWT + HttpOnly Cookie 的认证方案，配合 Passport.js 的 JWT Strategy。

## 理由
**AI 初稿建议：**  
AI 建议使用 Session + Redis 的方案，认为 Session 可即时撤销、安全性更高，并推荐使用 OAuth2 第三方登录（如微信/QQ 登录）降低注册门槛。

**人工修订：**

1. 选择 JWT 而非 Session：
    - 无状态验证减少数据库/Redis 查询，降低延迟
    - 7 天有效期的 HttpOnly Cookie 平衡了安全与体验
    - 对于校园级应用，JWT 无法即时撤销的缺点可通过黑名单机制（如需要时引入）弥补
2. 拒绝第三方 OAuth 登录：
    - 项目要求南大 smail 邮箱验证身份真实性，邮箱注册直接满足这一约束
    - 引入微信/QQ OAuth 需要企业资质审核，对校园项目不现实
    - 调研显示 80% 用户要求学号/邮箱验证，第三方登录无法满足此需求
3. WebSocket 认证：连接建立时从 Cookie 或 query 参数中提取 JWT 验证

## 后果
+ 正面影响：无状态认证简化服务端实现，HttpOnly Cookie 防 XSS 窃取
+ 负面影响：JWT 一旦签发无法即时撤销（除非引入黑名单）
+ 需要关注的风险：Cookie 的 CSRF 风险需通过 SameSite 属性和 CORS 配置 mitigated

## AI 辅助记录
+ AI 初稿内容摘要：推荐 Session + Redis + OAuth2，强调安全性和用户体验
+ 人工修订内容：改为 JWT + Cookie + 邮箱注册
+ 修订理由：AI 未考虑项目对南大邮箱验证的强制需求（80% 用户调研诉求），也未考虑第三方 OAuth 在校园项目中需要企业资质的现实约束。JWT 无状态特性更适合校园级应用的规模
