> Violet 校园恋爱辅助平台中应用的设计模式

## 模式一：状态模式（State Pattern）

### 应用场景：关系生命周期管理

系统中 Relationship（关系）具有明确的状态机：

```
MATCHING ──→ ICEBREAKING ──→ FLIRTING ──→ ENDED
```

每个状态转换触发不同的业务行为：
- MATCHING → ICEBREAKING：创建系统消息"破冰聊天已开启"
- ICEBREAKING → FLIRTING：移除军师、交换联系方式、聊天室变为只读
- * → ENDED：发送结束消息、清理 Redis 在线状态、断开连接

### 实现方式

当前代码中通过 `ChatLifecycleService.transitionStatus()` 方法实现：

```typescript
async transitionStatus(relationshipId, newStatus) {
  const oldStatus = relationship.status;

  if (oldStatus === 'MATCHING' && newStatus === 'ICEBREAKING') {
    return this.onIcebreaking(relationshipId);
  }
  if (oldStatus === 'ICEBREAKING' && newStatus === 'FLIRTING') {
    return this.onFlirting(relationshipId);
  }
  if (newStatus === 'ENDED') {
    return this.onEnded(relationshipId);
  }
}
```

每个状态转换的行为被封装在独立的私有方法中（`onIcebreaking`、`onFlirting`、`onEnded`），返回统一的 `LifecycleEvent` 结构。

### 为什么使用这个模式

- **状态行为差异大**：每个状态转换触发的操作完全不同（创建消息 vs 移除军师 vs 清理 Redis），将它们封装在独立方法中避免了一个巨型 switch-case
- **便于扩展**：如果将来新增状态（如 `DATING` 约会期），只需新增 `onDating()` 方法，不影响已有状态的处理逻辑
- **统一事件模型**：所有转换返回 `LifecycleEvent`，调用方（ChatGateway）只需处理统一的事件类型

### 如果不用这个模式会怎样

如果不使用状态模式，所有转换逻辑会堆在 `transitionStatus()` 一个方法中，导致：
- 该方法膨胀到 200+ 行
- 每个状态转换的修改都可能影响其他转换
- 测试困难——无法单独测试某个转换的行为
- 新增状态需要在长方法中插入新的 if 分支，容易遗漏或冲突

## 模式二：策略模式（Strategy Pattern）

### 应用场景：军师介入模式

系统中军师有三种介入模式，每种模式决定了不同的行为策略：

| 模式 | 主窗口消息 | 草拟消息 | 可见性 |
|------|----------|---------|--------|
| SOLO（代聊） | 军师可直接发送，伪装为当事人 | 不可用 | 军师可见主窗口消息 |
| PRIVATE（私聊） | 军师不可发送 | 不可用 | 军师不可见主窗口消息 |
| ASSIST（辅助） | 军师不可直接发送 | 军师可草拟，当事人确认后发送 | 军师可见主窗口消息 |

### 实现方式

当前代码中通过 `computeVisibility()` 方法实现策略选择：

```typescript
computeVisibility(message, viewerId, viewerRole, wingmanMode1, wingmanMode2) {
  if (message.type === 'MAIN') {
    if (viewerRole === 'wingman1' || viewerRole === 'wingman2') {
      const mode = viewerRole === 'wingman1' ? wingmanMode1 : wingmanMode2;
      if (mode === 'SOLO' || mode === 'ASSIST') {
        return { canSee: true, displaySenderId: message.senderId };
      }
      return { canSee: false, ... }; // PRIVATE mode
    }
  }
  // ... 其他消息类型处理
}
```

以及 `handleSendMessage()` 中的发送策略：

```typescript
if (member.role === 'wingman1' || member.role === 'wingman2') {
  const mode = member.wingmanMode;
  if (type === 'MAIN' && mode === 'SOLO') {
    effectiveSenderId = /* 替换为当事人ID */;
  } else if (type === 'MAIN' && mode === 'ASSIST') {
    // 禁止直接发送，必须用 draftMessage
  } else if (type === 'MAIN' && mode === 'PRIVATE') {
    // 完全禁止发送主窗口消息
  }
}
```

### 为什么使用这个模式

- **三种模式行为差异大**：同一条消息在不同模式下有不同的可见性和发送权限，策略模式让每条规则独立可维护
- **运行时切换**：当事人可以随时通过 `switchMode` 事件切换军师模式，策略在运行时动态选择
- **组合使用**：同一个聊天室中，两侧军师可以分别使用不同的模式（如 wingman1 用 SOLO，wingman2 用 PRIVATE），策略选择基于 `wingmanMode1` 和 `wingmanMode2` 分别计算

### 如果不用这个模式会怎样

如果不将模式行为策略化：
- 消息可见性和发送逻辑会在 ChatGateway 和 ChatService 中散布大量 `if (mode === 'SOLO') ... else if (mode === 'PRIVATE') ...` 判断
- 新增一种模式（如 `OBSERVE` 观察模式）需要找到所有包含 mode 判断的位置逐一修改
- 不同模式的行为规则难以集中理解和测试

## 模式三：观察者模式（Observer Pattern）

### 应用场景：WebSocket 实时事件推送

Socket.io 本质上是观察者模式的实现。ChatGateway 作为事件总线，各客户端 Socket 作为观察者：

```
ChatGateway (Subject)
    │
    ├── client1 Socket (Observer) ── 订阅 room:relationshipId
    ├── client2 Socket (Observer) ── 订阅 room:relationshipId
    ├── wingman1 Socket (Observer) ── 订阅 room:relationshipId
    └── wingman2 Socket (Observer) ── 订阅 room:relationshipId
```

### 实现方式

```typescript
// 加入房间（订阅）
client.join(roomId);

// 广播到房间（通知所有观察者）
this.server.to(roomId).emit('newMessage', message);

// 定向通知（只通知特定观察者）
this.server.to(socketId).emit('wingmanAssigned', data);
```

关键方法：
- `broadcastToVisibleMembers()`：根据可见性策略，只通知能看到的成员
- `emitToUsers()`：定向推送给指定用户列表
- `emitWingmanAssigned()` / `emitWingmanApproved()`：跨模块事件通知

### 为什么使用这个模式

- **实时通信的天然需求**：多方聊天需要实时推送消息给所有在线成员
- **解耦发送者和接收者**：消息发送者不需要知道谁会收到消息，由 `computeVisibility` 决定可见性
- **跨模块通信**：WingmanTaskController 通过 ChatGateway 推送通知，模块间松耦合

### 如果不用这个模式会么样

- 需要手动维护"谁在哪个聊天室"的映射关系
- 每次发送消息需要遍历所有连接查找目标用户
- 无法利用 Socket.io 的房间管理和自动重连机制

## 模式四：守卫模式（Guard / Chain of Responsibility）

### 应用场景：请求认证和权限校验

NestJS 的 Guard 机制本质上是责任链模式的变体：

```
HTTP Request
    │
    ▼
JwtAuthGuard ──→ 验证 JWT Cookie ──→ 通过？
    │                                │
    │ 是                             │ 否 → 401
    ▼
AdminGuard ──→ 验证 ADMIN 角色 ──→ 通过？
    │                                │
    │ 是                             │ 否 → 403
    ▼
Controller Handler
```

### 实现方式

```typescript
// 基础认证守卫
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  getRequest(context) { return context.switchToHttp().getRequest(); }
}

// 管理员守卫（链式继承）
@Injectable()
export class AdminGuard extends JwtAuthGuard {
  async canActivate(context) {
    const isAuthenticated = await super.canActivate(context); // 先验证 JWT
    if (!isAuthenticated) return false;

    const user = await this.prisma.user.findUnique({ ... });
    if (!user?.roles.includes('ADMIN')) {
      throw new ForbiddenException('需要管理员权限');
    }
    return true;
  }
}
```

### 为什么使用这个模式

- **声明式权限控制**：通过装饰器 `@UseGuards(JwtAuthGuard)` 或 `@UseGuards(AdminGuard)` 在 Controller 级别声明权限，代码清晰
- **可组合**：AdminGuard 继承 JwtAuthGuard，形成认证+授权的责任链
- **全局应用**：部分路由全局应用 Guard（如 `/user`、`/discovery`），部分路由单独配置（如 `/auth/register` 无需认证）

### 如果不用这个模式会怎样

- 每个 Controller 方法需要手动编写认证和权限检查代码
- 认证逻辑分散在各处，容易遗漏
- 修改认证机制（如从 Cookie 切换到 Bearer Token）需要修改所有方法

## 模式使用总结

| 设计模式 | 应用场景 | 解决的问题 | 代码位置 |
|---------|---------|-----------|---------|
| **状态模式** | 关系生命周期状态机 | 封装不同状态转换的业务行为 | `ChatLifecycleService.transitionStatus()` 及 `onXxx()` 方法 |
| **策略模式** | 军师介入模式（SOLO/PRIVATE/ASSIST） | 运行时动态选择消息可见性和发送策略 | `ChatService.computeVisibility()`、`ChatGateway.handleSendMessage()` |
| **观察者模式** | WebSocket 实时事件推送 | 多方实时通信、消息广播、跨模块通知 | `ChatGateway` 通过 Socket.io 的 room 机制 |
| **守卫/责任链模式** | JWT 认证 + 管理员权限 | 声明式权限控制、认证授权分层 | `JwtAuthGuard`、`AdminGuard` |
