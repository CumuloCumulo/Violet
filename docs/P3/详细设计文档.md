## 一、项目概述

Violet 是一个面向南京大学的校园恋爱辅助平台，核心创新在于引入"军师（Wingman）"角色帮助当事人破冰和聊天。

### 技术栈

| 层 | 技术 |
|----|------|
| 前端 | React 19 + TypeScript + Vite 8 + Tailwind CSS 4 + Zustand |
| 后端 | NestJS 11 + TypeScript + Socket.io 4 |
| 数据库 | PostgreSQL 16 + Prisma 6 |
| 缓存 | Redis 7（在线状态、待处理提议） |
| 认证 | JWT + HttpOnly Cookie |
| 部署 | 阿里云 ECS + Nginx + PM2 |

### 系统架构

```
Browser ──HTTP/WS──→ Nginx(:80) ──→ NestJS(:3000) ──→ PostgreSQL + Redis
```

后端采用单体分层架构，按业务领域划分为 8 个 NestJS 模块：

| 模块 | 职责 |
|------|------|
| AuthModule | 用户注册、登录、JWT 签发 |
| UserModule | 个人资料管理、头像上传、军师认证 |
| DiscoveryModule | 用户浏览、牵线请求、关系列表 |
| ChatModule | 实时聊天（HTTP + WebSocket）、消息可见性、关系生命周期 |
| WingmanTaskModule | 军师任务大厅、申请、审批 |
| CreditModule | 信用分余额、签到、扣减 |
| AdminModule | 平台统计、用户管理、信用分调整 |
| PrismaModule | 数据库连接管理 |

## 二、类图设计摘要

系统核心类共 18 个，分为 5 层：

- **Controller 层**（7 个）：AuthController、UserController、DiscoveryController、ChatController、WingmanTaskController、CreditController、AdminController
- **Gateway 层**（1 个）：ChatGateway
- **Service 层**（9 个）：AuthService、UserService、DiscoveryService、ChatService、ChatLifecycleService、RoomService、PresenceService、WingmanTaskService、CreditService、AdminService
- **Guard 层**（2 个）：JwtAuthGuard、AdminGuard
- **数据层**（1 个）：PrismaService

最复杂的类是 ChatGateway（~695 行），协调 ChatService、RoomService、PresenceService、ChatLifecycleService 四个 Service 处理 10 种 WebSocket 事件。

详细类图见 [类图.md](./类图.md)。

## 三、SOLID 检查摘要

对 AI 生成的代码进行了逐条 SOLID 审查，发现以下问题：

| SOLID 原则 | 违反数量 | 最严重问题 |
|-----------|---------|-----------|
| S - 单一职责 | 3（1 严重） | ChatGateway 承担 7 项职责 |
| O - 开闭原则 | 3（2 严重） | 新增消息类型/军师模式需修改多处 if/else |
| L - 里氏替换 | 0 | 无违反 |
| I - 接口隔离 | 2（1 严重） | Service 直接依赖完整 PrismaService |
| D - 依赖倒转 | 4（设计权衡） | Service 与 Prisma/ioredis 耦合 |
| **总计** | **12** | |

其中 4 处 D 原则违反为有意识的设计权衡——在 4 人团队、10 周开发周期约束下，Prisma 的类型安全和开发效率收益大于抽象 Repository 层的架构收益。

详细检查见 [SOLID检查清单.md](./SOLID检查清单.md)。

## 五、数据库设计摘要

### ER 模型

系统包含 12 个核心实体：User、Relationship、WingmanAssignment、WingmanTask、WingmanApplication、Message、MatchRequest、Rating、Post、PostReply、CheckinRecord、CreditLog。

### 关键关系

- User 与 Relationship：多对多（通过 user1Id/user2Id）
- Relationship 与 WingmanAssignment：一对多（每侧最多 1 个军师，`@@unique([relationshipId, side])`）
- Relationship 与 Message：一对多
- WingmanTask 与 WingmanApplication：一对多（级联删除）

### 索引设计

共设计 7 个复合索引，覆盖最高频查询场景：
- `Message(relationshipId, createdAt)`：聊天记录加载
- `MatchRequest(toUserId, status)` / `(fromUserId, status)`：牵线请求列表
- `CheckinRecord(userId, createdAt)`：签到去重

### 隐私保护

- password：bcrypt 哈希（salt rounds = 10）
- wechat/qq/phone：仅在 FLIRTING（暧昧期）通过 contactExchange 事件交换
- email：API 响应中不对外暴露

详细设计见 [数据库设计.md](./数据库设计.md)。

## 六、设计模式应用摘要

系统中应用了 4 种设计模式：

| 模式 | 场景 | 优势 |
|------|------|------|
| 状态模式 | 关系生命周期（MATCHING→ICEBREAKING→FLIRTING→ENDED） | 封装不同状态转换的业务行为，便于扩展新状态 |
| 策略模式 | 军师介入模式（SOLO/PRIVATE/ASSIST） | 运行时动态切换消息可见性和发送策略 |
| 观察者模式 | WebSocket 实时事件推送 | 多方实时通信、消息广播、跨模块通知 |
| 守卫/责任链模式 | JWT 认证 + 管理员权限 | 声明式权限控制、认证授权分层 |

详细分析见 [设计模式.md](./设计模式.md)。

## 七、AI 协作说明

本阶段的详细设计文档中，类图、API 规范、数据库设计均为 AI 根据项目实际代码逆向提取和分析生成。SOLID 检查清单和设计模式分析是 AI 对自身生成的代码进行的审查和反思。

AI 在以下方面表现良好：
- 从代码中准确提取类结构、方法签名和类间关系
- 识别 SOLID 违反并给出合理的修正方案
- 识别设计模式的应用场景并分析利弊
- 生成规范的 SQL 建表语句和索引设计

AI 的局限：
- 对"设计权衡"的判断力不足（如 D 原则违反是否值得修复）
- 倾向于建议过度抽象（如建议为所有 Service 引入 Repository 接口）
- 缺乏对团队规模和项目周期的考虑（4 人 10 周的项目不应追求完美的 SOLID 合规）
