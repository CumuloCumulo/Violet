## 2. AI 助力分析（Q1）

AI 在本项目中发挥了显著作用，主要体现在以下方面：

**1. 逆向文档生成能力突出**

P3 阶段最大的助力是 AI 从已有代码中逆向提取设计文档。项目采用"先开发后文档"的 MVP 策略——功能在 P2 阶段就已通过 openspec 驱动开发完成。P3 要求提交类图、API 文档、ER 图等交付物时，AI 能够从 Controller、Service、Gateway、Prisma schema 等源码中准确提取完整信息：
- 从 9 个 Controller 文件提取 36 个 API 接口的路径、参数、响应格式
- 从 Prisma schema 提取 12 个模型的实体关系和索引设计
- 从 18 个核心类中梳理出完整的类图（属性、方法、关联/依赖/继承关系）

这比手动编写节省了大量时间，且准确度高——因为文档直接来自代码，不存在文档与代码不一致的问题。

**2. openspec 驱动开发流程的契合**

AI 与 openspec 工作流高度契合。每个功能模块的开发遵循 proposal → design → spec → tasks 的流程：
- AI 根据 proposal 理解需求背景和目标
- 根据 design 中的技术决策生成实现代码
- 根据 spec 中的 GIVEN/WHEN/THEN 场景验证实现完整性
- 根据 tasks 清单逐项推进

这种结构化的 prompt 上下文远优于零散的需求描述，AI 输出质量因此稳定在 4-5 分。

**3. 代码审查和模式识别**

AI 在 SOLID 检查中识别出了 12 处违反，并对每处给出了具体的修正方案。在设计模式分析中准确识别了 4 种设计模式并解释了各自的应用场景。这些分析对理解项目的架构设计有很大帮助。

## 3. AI 误导分析（Q2）

SOLID 检查中发现的 AI 设计问题数量：**12 处**（S:3, O:3, L:0, I:2, D:4）

最严重的设计问题是：**ChatGateway 违反单一职责原则**——该类承担了 WebSocket 连接管理、消息路由、可见性过滤、模式切换、状态广播、通知推送等 7 项职责，代码约 695 行。

**AI 在设计层面的误导倾向：**

1. **过度设计倾向**：SOLID 检查中 AI 建议为所有 Service 引入 Repository 接口层、抽象密码和 token 库。在 4 人团队、10 周开发周期的约束下，这些抽象带来的维护成本超过了收益。AI 倾向于追求理论上的架构完美，而不考虑项目实际规模。

2. **忽视 MVP 策略**：AI 的修正方案倾向于一次性解决所有问题（如拆分 ChatGateway 为 NotificationService + WingmanModeService + ...），而实际开发中应优先保证功能交付，渐进式重构。

3. **设计权衡缺乏判断**：D 原则的 4 处违反实际上都是有意识的设计权衡（直接使用 PrismaService 换取类型安全），AI 在初期审查时将其标记为"违反"，未能区分"不知道 D 原则"和"有意识地接受权衡"。

4. **代码生成中的边界问题**：在功能开发中，AI 有时会生成超出 spec 范围的额外代码（如添加不必要的错误处理、过度校验），需要人工删减约 20-30%。

## 4. Prompt 改进计划（Q3）

上阶段改进措施的验证结果：

在 P2 阶段，团队意识到"提供项目约束（团队规模、开发周期）给 AI 可以显著改善输出质量"。在 P3 中验证了这一点——当我们在 SOLID 检查的 prompt 中明确说明"4 人团队、10 周开发周期"的约束后，AI 能够识别出哪些违反是"设计权衡"而非"设计缺陷"。openspec 驱动开发的实践也证实了：结构化的 spec（含 GIVEN/WHEN/THEN 场景）比自由描述产生更高质量的 AI 输出。

本阶段新的改进措施：

1. **"先开发后文档"策略得到验证**：通过 openspec 驱动先完成功能实现，再让 AI 逆向生成文档，避免了"文档先行"中常见的文档与代码不一致问题。后续项目可延续此模式。

2. **AI 审查需加"约束前缀"**：让 AI 审查设计时，应在 prompt 开头明确项目的团队规模、时间约束和技术栈偏好，避免 AI 给出脱离实际的过度设计建议。

3. **对 AI 的 SOLID 建议分级处理**：将 AI 发现的问题分为"必须修复"、"建议修复"和"可接受的权衡"三级，而非全盘接受。本次实践中 D 原则的 4 处违反均为可接受的权衡。

## 5. 本阶段的核心工程判断

决策内容：采用 MVP 策略 + openspec 驱动开发，先完成功能实现再逆向生成 P3 设计文档，而非按照传统瀑布流程先完成类图和 API 文档再编码。

为什么 AI 无法做这个决策：

1. **AI 无法评估团队的开发能力和节奏**：AI 不知道团队成员有丰富的开发经验，能够直接通过 spec 驱动高质量编码。AI 默认假设团队需要完整的文档指导才能开发。

2. **AI 不理解课程作业的效率最优解**：AI 倾向于按文档字面顺序执行（先类图 → 再 API → 再数据库），而不会质疑"是否可以同时开发和设计"。

3. **AI 缺乏对交付物价值的判断力**：AI 无法判断哪些文档对实际项目有增量价值（如从代码逆向生成的文档比凭空设计的文档更准确），哪些只是为了满足课程要求的形式主义。

4. **"可接受的技术债"需要人的判断**：ChatGateway 695 行是否需要拆分？PrismaService 直接注入是否可接受？这些决策取决于团队规模、项目阶段和未来计划，AI 无法做出合理的权衡。
