## 1. 引言

### 1.1 目的

本文档是 Violet 校园恋爱代聊平台的需求规格说明书，旨在明确系统的功能需求、非功能需求及约束条件，作为后续系统设计、开发与测试的基准参考。

### 1.2 范围

Violet 是一个面向南京大学在校学生的匿名恋爱破冰与牵线平台。平台核心功能包括：基于标签的用户发现与匿名牵线、军师（恋爱顾问）辅助聊天系统（含代聊模式）、游戏化三阶段关系推进（牵线期→破冰期→暧昧期）、信用分经济体系、帖子大厅社区。

平台定位为**"破冰与牵线跳板"**——帮助用户完成从陌生人到建立联系的过程，而非替代日常恋爱沟通工具。当双方关系推进到一定阶段后，平台引导用户转移到微信/QQ 等外部工具继续发展。

### 1.3 定义与缩写

| 术语 | 定义 |
|------|------|
| 当事人 | 在平台中寻找恋爱对象的用户角色 |
| 军师 | 辅助当事人破冰、聊天、出谋划策的用户角色 |
| 牵线期 | 关系推进第一阶段，双方匿名初步接触 |
| 破冰期 | 关系推进第二阶段，双方解锁身份，军师可介入 |
| 暧昧期 | 关系推进第三阶段，平台交换联系方式，聊天关闭 |
| 信用分 | 平台核心虚拟货币，用于牵线消费、军师准入等 |
| Solo 模式 | 军师直接以当事人身份发送消息的代聊模式 |
| 辅助模式 | 军师草拟消息，当事人确认后发送的模式 |
| 私聊模式 | 军师仅与当事人私聊，无法看到当事人间对话的模式 |
| NTR | "爱上军师"风险，即对方好感错位至军师 |

## 2. 总体描述

### 2.1 产品视角

Violet 是一个独立运行的 Web 应用，采用前后端分离架构。后端基于 NestJS，前端基于 Vue 3 + Vite，实时通信使用 WebSocket。平台不依赖第三方社交 API，不接入复杂推荐算法。

### 2.2 用户特征

平台涉及三类用户角色：

| 角色 | 描述 | 特征 |
|------|------|------|
| 当事人 | 寻找恋爱对象的核心用户 | 以大一、大二学生为主（80%~95%），约 30%~41% 正在寻找恋爱关系；核心痛点是"缺乏渠道"（87%）和"不敢主动"（73%） |
| 军师 | 为当事人提供恋爱辅助的用户 | 81% 受访者有意愿成为军师；核心驱动力为"吃瓜/看真实恋爱案例"（87.5%）和"成就感"（45.8%）；需通过道德审核和资质认证 |
| 管理员 | 后台管理人员 | 负责信用分管理、用户封禁、退款处理等 |

同一用户可同时拥有"当事人"和"军师"两种前台身份。

### 2.3 运行环境

- **客户端**：现代浏览器（Chrome、Safari、Firefox 最新两个大版本），支持移动端自适应
- **服务端**：Node.js 环境，NestJS 框架
- **数据库**：关系型数据库（如 MySQL/PostgreSQL）
- **实时通信**：WebSocket

### 2.4 设计约束

- **CO-01** [人工补充]：必须使用南大 smail 邮箱注册，保证用户真实性（调研中 80% 用户要求学号验证）
- **CO-02** [人工补充]：平台不依赖复杂推荐算法（仅不足 30% 用户信任算法），以标签平铺展示为核心匹配逻辑
- **CO-03** [人工补充]：聊天仅支持文字和内置表情，禁止发送本地图片，防止违规内容传播
- **CO-04** [人工补充]：初期付费通过微信个人收款码人工处理，不集成第三方支付
- **CO-05** [人工补充]：军师强制退出机制——进入暧昧期后军师自动剥离，防止 NTR 风险

### 2.5 假设与依赖

- 假设用户拥有南大 smail 邮箱并能正常接收验证邮件
- 假设项目开发周期为 10 周，优先实现核心功能
- 假设初期用户量在百人级别，非功能需求以可用性为主而非高并发
