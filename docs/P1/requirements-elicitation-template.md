## 一、需求提取规则

### 1.1 需求编号规则

```
[类型]-[模块]-[序号]

类型:
- FR: Functional Requirement (功能需求)
- NFR: Non-Functional Requirement (非功能需求)
- CR: Constraint Requirement (约束需求)

模块:
- AUTH: 用户认证与授权
- USER: 用户管理
- MATCH: 匹配系统
- CHAT: 聊天系统
- STRAT: 军师系统
- PAY: 支付与货币
- PRIVACY: 隐私与安全
- NOTIFY: 消息通知
- ADMIN: 管理后台

示例: FR-AUTH-001, NFR-PERF-001
```

### 1.2 优先级定义

| 优先级 | 定义 | 说明 |
|-------|------|------|
| P0 (Must) | 必须实现 | 系统核心功能，缺失则无法正常运行 |
| P1 (Should) | 应该实现 | 重要功能，影响用户体验 |
| P2 (Could) | 可以实现 | 锦上添花的功能 |
| P3 (Won't) | 暂不实现 | 明确排除的功能 |

### 1.3 需求来源标注

- `[问卷N]`: 来自第N题问卷结果
- `[访谈-P]`: 来自访谈对象P
- `[观察]`: 来自用户行为观察
- `[推断]`: 基于数据的合理推断

## 四、需求质量检查清单

在完成需求提取后，逐项检查:

### 4.1 完整性检查
- [ ] 每条需求都有唯一编号
- [ ] 每条需求都有明确描述
- [ ] 每条需求都有验收标准
- [ ] 每条需求都标注了优先级
- [ ] 每条需求都记录了数据来源

### 4.2 规范性检查
- [ ] 需求描述使用"系统必须/应该/可以"开头
- [ ] 验收标准可量化、可测试
- [ ] 避免使用模糊词汇（如"良好"、"快速"等）

### 4.3 一致性检查
- [ ] 需求之间无矛盾
- [ ] 术语定义统一
- [ ] 优先级判断合理

### 4.4 可追溯性检查
- [ ] 每条需求都能追溯到调研数据
- [ ] 重要决策有数据支撑

## 五、基于调研数据的关键发现

### 5.1 需求优先级调整依据

根据调研结果，以下发现影响优先级判断:

| 发现 | 数据支持 | 对需求的影响 |
|------|---------|-------------|
| 代聊接受度低 | 仅32.43%可接受 | 降低"4人对话"相关需求优先级 |
| 隐私安全顾虑高 | 86.49%最担心隐私泄露 | 提升安全相关需求至P0 |
| 实名认证需求高 | 78.38%要求学号验证 | FR-AUTH-001必须实现 |
| 对算法匹配信任一般 | 56.76%主要看个人判断 | 算法匹配功能降为P1/P2 |

### 5.2 需求取舍决策

| 决策 | 理由 | 数据支撑 |
|------|------|---------|
| 示例: 不强制要求4人对话 | 40.54%认为没必要 | 问卷Q10 |
| 示例: 增加一对一私聊选项 | 用户更偏好一对一 | 问卷Q10推断 |
